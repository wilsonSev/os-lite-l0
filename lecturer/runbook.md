# Почему упал myITMO: первое дежурство

Сценарий демонстрационной H0 на 90 минут. Слева — одна мысль, справа — терминал.
Студенты в основном не печатают: предсказывают вывод, выбирают следующий шаг
и формулируют заключение. Самостоятельное повторение — после занятия.

## Результат занятия

Студент понимает, как из жалобы получить проверяемый факт: найти файл,
отделить ошибки от результатов, соединить команды, прочитать статус,
передать путь с пробелами, остановить фоновый процесс. После самостоятельных
упражнений сможет повторить эти действия руками.

История: открылась выборность курсов, выбор не сохраняется, расписание не грузится.
Мы дежурная команда. Вместо «всё лежит» к концу получим короткое заключение с уликами.
Сервис не запускаем и не ремонтируем. Все события и архитектура вымышлены;
это не расследование настоящего myITMO. Настоящие здесь файлы, процессы и shell.

Материалы ведущего: [подготовка](preparation.md),
[шпаргалка](cheatsheet.md), [эталоны](expected-output.md).
Весь набор команд ниже выполняется в интерактивном Bash из корня репозитория.

## Как вести

Цикл: **зачем → маленькая модель → команда без Enter → прогноз → запуск → вывод**.
На прогноз дать 15–20 секунд. Вопрос должен требовать применения уже показанной
модели, а не угадывания названия новой утилиты. Ошибка запланированного примера —
полезная остановка, не повод срочно спрятать терминал.

Не показывать README с разгадкой на старте. Не читать вслух весь скрипт.
Не превращать разбор пула соединений в лекцию про БД: хватит аналогии с кассами.
В таблицах ниже «слева» — текст для слайда или устного пояснения, не готовый слайд-дек.

## 0–6. Завязка: студентам нужно расписание

**Слева:** «Жалоба → вопрос → данные → вывод».

**Сказать:**

> Открылась выборность. Ты выбрал курс, нажал сохранить — ошибка. Обновил страницу —
> расписания нет. В чате уже “Мой ИТМО лежит”. Сегодня мы по другую сторону:
> дежурная команда, у которой есть терминал и журнал. Наша задача — объяснить,
> что мешает выбору курсов, и подтвердить ответ данными.

**Спросить:** «Фраза “всё лежит” — диагноз? Что уточним первым?»
Ожидаем: что работает, что не работает, когда началось, какие ошибки.
Не требовать слова `grep`.

Показать `ls logs` — есть журнал. Причину пока не раскрывать.
Организационные ссылки и дедлайны показать в начале, если они уже определены курсом.
Фраза про SSH: «На реальном дежурстве мы могли бы подключиться к серверу по SSH;
сегодня уже находимся в учебном терминале».

**Только для заранее проверенного Docker-варианта:** на 3–6 минуте можно за 30 секунд
показать `./check --docker`: «Позже объясним, как запускается учебная проверка».
Это проверка hello.txt, не здоровья myITMO. На текущей машине без Docker этот
вставной показ пропустить. Не начинать занятие с установки или ошибки Docker.

**Переход:** «Первый шаг расследования — понять, где мы и где данные».

## 6–13. Улики лежат в файлах

**Слева:** «Команда + аргументы. Относительный путь зависит от текущей папки».

```bash
pwd
ls
ls -l logs
cd logs
pwd
ls
cd ..
```

Показать дополнение Tab на `logs/`, возврат к команде стрелкой ↑.
После объяснения `cd` спросить: «Мы переместили журнал или сменили текущую папку?»
Ответ: только сменили папку, файл остался на месте.

```bash
man tail
```

Показать поиск `/follow`, выход q. Если man не установлен — не чинить на занятии;
открыть подготовленную шпаргалку. `less logs/myitmo.log` и Ctrl-R — только при запасе.
Не обещать `--help` любой Unix-команде на любой ОС.

**Переход:** «Найти данные мало. Нужно сохранить результаты, не потеряв ошибки».

## 13–20. Результат и ошибка идут разными дорогами

**Слева:** `stdin (0) → процесс → stdout (1)`; отдельно `stderr (2)`.
Сначала дать модель, затем намеренно обратиться к отсутствующему файлу:

```bash
ls exists.txt missing.txt
```

**Сказать:** «Одна команда смогла показать существующий файл и сообщила о проблеме
с другим. Это два разных потока».

**Набрать без Enter:**

```bash
ls exists.txt missing.txt > output.txt
```

**Спросить:** «Всё уйдёт в файл или что-то останется на экране?»
Ответ: имя — в файле, ошибка — на экране. Затем разделить потоки явно:

```bash
ls exists.txt missing.txt > output.txt 2> errors.txt
cat output.txt
cat errors.txt
echo again >> output.txt
cat output.txt
```

Пояснить `>` — перезапись, `>>` — дописывание. Ошибка здесь запланирована.
Текст сообщения и ненулевой код `ls` могут различаться между ОС.

**Сказать:** «Следующую команду можно кормить результатом предыдущей вместо файла».

```bash
cat exists.txt | wc -l
```

Прогноз: число 1. `|` передаёт stdout в stdin, а не текст набранной команды.
`/dev/null` — место, куда можно отправить ненужный вывод; ошибки не исчезают
из смысла операции только потому, что мы перестали их видеть.

**Переход:** «Как тогда автоматически понять, сработала ли команда?»

## 20–26. Тишина не равна успеху

**Слева:** «Текст — для человека. Код возврата — для следующего действия».

```bash
ls missing.txt 2>/dev/null
echo "$?"
ls exists.txt >/dev/null
echo "$?"
```

Первая команда молчит, но код ненулевой; у второй — 0.
Читать `$?` сразу: после `echo` это уже код `echo`.

```bash
ls exists.txt >/dev/null && echo 'Файл доступен'
ls missing.txt 2>/dev/null || echo 'Нужно проверить путь'
```

Прогноз: когда выполнится правая часть? `&&` при 0, `||` при ненулевом коде.
Оговорить: значение кода задаёт команда; например, grep использует 1 для отсутствия
совпадений, а не только для «аварии». Вернёмся к этому на скрипте.

**Переход:** «Теперь можем не только увидеть ошибку, но и действовать по результату.
Вернёмся к жалобе студентов».

## 26–42. Выбор курсов не сохраняется: ищем общий симптом

**Слева:** «Отфильтровать → выделить поле → сгруппировать → посчитать».
Генератор пока выключен, после setup в журнале ровно 10000 строк.

```bash
cat logs/myitmo.log
```

Разобрать одну строку: UTC-время, уровень, endpoint, HTTP-статус, событие.
Endpoint — какое действие запросили. `/enroll` сохраняет выбор,
`/courses` показывает курсы, `/schedule` загружает расписание.
Пояснить 200 — успешный ответ, 503 — сервис не смог обслужить запрос.

**Сказать:** «На экране десять строк для обучения. Команду хотим такую,
чтобы она не зависела от того, десять строк здесь или сто тысяч».

### Оставляем только ошибки

```bash
grep ' ERROR ' logs/myitmo.log
```

Это фильтр строк с заданным текстом. Спросить, что хотим узнать дальше: количество.

```bash
grep ' ERROR ' logs/myitmo.log | wc -l
```

Прогноз: число, не список; результат 5.

### Какое действие чаще встречается среди ошибок?

Каждый следующий вариант набрать отдельно, показать изменившийся результат:

```bash
grep ' ERROR ' logs/myitmo.log | cut -d' ' -f3
```

Третье поле — `endpoint=...`. У нашего формата ровно один пробел между полями.
Затем добавить `sort`, затем `uniq -c`, затем итоговую сортировку:

```bash
grep ' ERROR ' logs/myitmo.log \
  | cut -d' ' -f3 \
  | sort | uniq -c | sort -nr
```

Ожидаем: 3 `/enroll`, 1 `/schedule`, 1 `/courses`.
Вопрос: «Почему нельзя выкинуть первый sort?» — uniq объединяет только соседние
одинаковые строки. Для top-1 можно добавить `| head -n 1`.
Рейтинг показывает число ошибок в выборке, не сравнение процентов отказов.

### Что объединяет разные действия?

```bash
grep ' ERROR ' logs/myitmo.log \
  | cut -d' ' -f5 | sort | uniq -c
grep 'endpoint=/health ' logs/myitmo.log
```

5 раз `event=db_pool_timeout`. При этом `/health` успешен.

**Сказать:** «Пул — набор соединений, через которые приложение обращается к БД.
Представьте кассы: когда все заняты, следующий посетитель ждёт. Здесь запрос
не дождался соединения. Это ещё не доказывает, что сама база выключена».

**Спросить:** «Какие данные помогут проверить эту версию?»
Ответ: сколько соединений занято, каков лимит, есть ли очередь.

**Переход:** «Смена оставила диагностический снимок. Попробуем его открыть».

## 42–50. Пробел в имени файла скрывает улику

**Слева:** «Кавычки сохраняют значение одним аргументом».

```bash
file='my log.txt'
cat $file
```

Сначала показать присваивание без пробелов вокруг `=`. Перед второй командой
спросить, сколько аргументов получит cat. После ошибки объяснить: `my` и `log.txt`.

```bash
cat "$file"
```

Теперь доступны две строки метрик и заметка:

- до открытия выбора `active=4`, `limit=20`, `waiting=0`, `incoming_rps=15`;
- после — `active=20`, `limit=20`, `waiting=180`, `incoming_rps=800`;
- `/courses`, `/enroll`, `/schedule` используют этот пул; `/health` не использует БД.

**Спросить:** «Сформулируйте, почему не сохраняется выбор, без фразы “всё сломалось”».
Ожидаем: все соединения заняты, запросы ждут и получают таймаут.
Это фиксированный снимок инцидента, а не метрики нашей машины или текущего генератора.
Рост запросов виден, но для объяснения долгой занятости соединений нужны дальнейшие данные.

```bash
echo '$file'
echo "$file"
count=$(grep -c ' ERROR ' logs/myitmo.log)
echo "$count"
```

Одинарные кавычки сохраняют буквальный текст, двойные допускают подстановку;
`$(...)` берёт stdout команды. `export LC_ALL=C` из подготовки — пример передачи
настройки дочерним процессам. Подробный PATH и окружение оставить на следующий раз.

**Переход:** «Снимок объясняет прошлое. Как наблюдать за новыми событиями?»

## 50–56. Терминал занят, но расследование продолжается

**Слева:** «Просмотр журнала и источник событий — два процесса».

```bash
./scripts/generate-log.bash &
GEN_PID=$!
jobs
tail -f logs/myitmo.log
```

События появляются раз в секунду. `&` запускает в фоне, `$!` — PID последнего
фонового запуска. Подождать 2–3 строки, нажать Ctrl-C.

**Прогноз до Ctrl-C:** «Остановится просмотр или ещё и источник событий?»
Ответ: только tail. Показать jobs — генератор ещё работает в этой оболочке.

```bash
kill "$GEN_PID"
wait "$GEN_PID"
./reset-demo
```

`kill` здесь посылает сигнал завершения, `wait` дожидается остановки.
Сброс снова даёт 10000 строк и 5 ошибок. Это восстановление учебных данных, не ремонт БД.
Не считать ошибки на меняющемся журнале и не обещать фиксированные числа без reset.

Если осталось время: на `sleep 60` показать Ctrl-Z → jobs → bg → fg → Ctrl-C.
Ctrl-Z приостанавливает, Ctrl-C прерывает. Не оставлять пример работать после блока.

## 56–63. Передаём следующей смене проверку

**Слева:** «Повторяемое действие можно сохранить в скрипт».

```bash
./scripts/healthcheck.bash
echo "$?"
./scripts/healthcheck.bash fixtures/myitmo.log.healthy
echo "$?"
```

Ожидаем FAIL/1 и OK/0. Это проверка всего файла на ERROR, не HTTP-проба текущего
сервиса: наличие старых ошибок не означает, что он всё ещё неисправен сейчас.

```bash
cat scripts/healthcheck.bash
```

Показать только shebang, grep и `exit 1`. Пояснить, что исполняемый бит уже
поставлен; его устанавливает `chmod +x scripts/healthcheck.bash`.
Не объяснять весь case и проверки входа построчно.

Если успеваем:

```bash
grep -c ' ERROR ' fixtures/myitmo.log.healthy
echo "$?"
```

Вывод 0, код 1: нет совпадений. Поэтому строгий режим нельзя объяснять одной фразой
«добавляйте всегда». `set -euo pipefail`, shellcheck, shfmt и написание скриптов —
продолжение курса, сегодня shellcheck лишь назвать инструментом поиска ошибок.

**Переход:** «Скрипт умеет вернуть результат. Как дать коллегам одинаковую среду запуска?»

## 63–75. Проверяем окружение — два честных маршрута

### Полная H0: Docker заранее проверен на машине ведущего

Условие: выполнены все шаги [подготовки](preparation.md), успешны hello-world
и `./check --docker`. Не устанавливать Docker на занятии.

**Слева:** «Образ — готовая среда; контейнер — её экземпляр; наши файлы снаружи».

**Сказать:** «На разных машинах отличаются утилиты и настройки. Контейнер помогает
зафиксировать среду проверки. Сейчас покажем механизм на тривиальном файле:
это отдельная проверка учебного задания, не проверка доступности myITMO».

```bash
docker run --pull=never --rm hello-world
cat check
./check --docker
```

Разобрать только образ, `--rm`, `-v host:container:ro`, `--pull=never`.
Образ скачан до пары. Не рассказывать про сети, build, namespaces и cgroups.
Здесь проверочный скрипт тоже примонтирован с хоста; в настоящем образе курса
он должен быть внутри образа. Официальный checker к этому репозиторию не подключён.

```bash
printf 'broken\n' > src/hello.txt
./check --docker
echo "$?"
printf 'Hello, OS Lite!\n' > src/hello.txt
./check --docker
```

FAIL/1 → PASS/0. Перед исправлением спросить: «Потребуется пересборка образа?»
Ответ: нет, мы меняем примонтированный файл.

Оставшиеся 3 минуты — отладка. Для диагностики сохранить контейнер (без `--rm`):

```bash
docker run --pull=never --name h0-debug \
  -v "$PWD/src:/workspace/src:ro" \
  -v "$PWD/scripts/demo-check.sh:/demo-check.sh:ro" \
  alpine:3.20 sh /demo-check.sh /workspace/src
docker ps -a
docker logs h0-debug
docker rm h0-debug
```

Имя должно быть свободно до занятия. После `--rm` контейнера уже нет — не пытаться
найти его логи. CI, защита и официальный образ объясняются как схема курса,
а не как уже настроенная инфраструктура этой площадки. Одинаковый образ помогает
воспроизводимости, но сам по себе не гарантирует одинаковый результат при разных входных данных.

### Текущая репетиция: Docker отсутствует или не проверен

**Сказать:** «В этом окружении Docker ещё не подготовлен. Сейчас проверим контракт
задания локально. Контейнерный запуск потребует отдельной репетиции».

```bash
./check --local
printf 'broken\n' > src/hello.txt
./check --local
echo "$?"
printf 'Hello, OS Lite!\n' > src/hello.txt
./check --local
```

За 4 минуты показать PASS/FAIL и объяснить, что проверяется одна строка.
Оставшиеся 8 минут использовать на повторение конвейера студентами или вопросы.
Если есть заранее сделанная запись Docker, показать её с явной пометкой «запись».
Если записи нет, не обещать её. Это репетиция shell-части, не выполненный Docker-блок H0.

## 75–82. Сдаём смену: три предложения вместо «всё лежит»

**Слева:** «Симптом → доказательство → следующая проверка».
Попросить аудиторию составить заключение. Не читать готовый ответ первым.

Ожидаем:

> Во время выбора курсов запросы к списку курсов, сохранению выбора и расписанию
> завершались 503. Во всех пяти ошибках — ожидание соединения с БД; снимок показывает
> 20 занятых соединений из 20 и очередь 180 запросов. Нужно исследовать длительность
> запросов, блокировки и возврат соединений; данных для конкретного исправления пока нет.

Дополнительный вопрос: «Почему зелёный `/health` не опровергает жалобу?»
Ответ: эта проверка не использует БД.
Не выдавать увеличение лимита соединений за доказанное решение.

Теперь возвращаемся к перенаправлению и сохраняем вывод для следующей смены:

```bash
printf '%s\n' \
  'Symptom: course selection and schedule requests return 503.' \
  'Evidence: db_pool_timeout; active=20/20; waiting=180.' \
  'Next: inspect slow queries, locks and connection release.' \
  > output.txt
cat output.txt
```

Спросить, почему `>` здесь допустим: перезаписываем известный демо-файл.
В реальном инциденте исходные логи сохраняют отдельно; здесь мы не меняли fixtures.

## 82–90. Проверка понимания и выход

Три коротких вопроса без подсказки команды:

1. Как посчитать не только ошибки, но и все события `/enroll`? Ответ: 4 события.
2. Как спрятать stderr, но сохранить возможность узнать об ошибке? Ответ: `2>/dev/null`, затем `$?`.
3. Что останется работать после Ctrl-C в tail? Ответ: фоновый генератор, если его не остановили.

При готовых ноутбуках 3–5 минут на `./setup` и первое упражнение; при подготовленном
Docker — hello-world. Остальные записывают ответы или объясняют соседу.
Не требовать установки в аудитории.

Выдать [упражнения](../exercises/README.md) и [шпаргалку](cheatsheet.md).
Практическая цель: повторить расследование, объяснить каждую стадию конвейера,
получить и исправить FAIL у checker. Локальный PASS не подтверждает настройку Docker.
Официальные сроки, suite и сдачу преподаватель сообщает по материалам курса.

После пары остановить генератор, восстановить hello.txt при необходимости,
выполнить `./reset-demo`. Не очищать чужие файлы и историю массовыми командами.
