# Самостоятельная практика после H0

Работайте в Bash из корня репозитория. Начните с `./setup`.
`./check` проверяет только демо-файл, остальные задания проверяются по ответам
ниже и наблюдениям. Ничего не отправляется автоматически.

1. Найдите журнал через `pwd`, `ls`, `cd`; вернитесь в корень. Найдите в
   `man tail`, что делает `-f`. Если справки нет, используйте материалы занятия.
2. Выведите только ERROR и посчитайте их. Постройте рейтинг endpoints,
   не редактируя fixture. Объясните роль каждой стадии конвейера.
3. Разделите stdout и stderr команды `ls exists.txt missing.txt` в два файла.
   Какой файл изменится после `echo again >> output.txt`?
4. Выполните `file='my log.txt'`, сравните `cat $file` и `cat "$file"`.
   Объясните число аргументов; не переименовывайте файл для обхода ошибки.
5. Запустите healthcheck на основном, healthy и отсутствующем журнале.
   Сразу после каждого запуска прочитайте `$?`. Куда выводится сообщение?
6. Запустите генератор в фоне, сохраните `$!`, откройте `tail -f`.
   После Ctrl-C проверьте `jobs`: что продолжает работать? Остановите генератор
   по сохранённому PID, дождитесь завершения, восстановите исходный лог.
7. Замените строку в `src/hello.txt` на `broken` и запустите `./check`.
   Верните файл командой `printf 'Hello, OS Lite!\n' > src/hello.txt`.
   Докажите успешный прогон и сравните коды. Сброс не исправляет этот файл за вас.
8. Если Docker подготовлен: выполните `./check --docker`, повторите шаг 7.
   Объясните, почему после изменения файла не требовалась пересборка образа.
   Если Docker не настроен, отметьте это отдельно: локальный PASS его не проверяет.

## Самопроверка

- После reset: 10000 строк, 5 ERROR; `/enroll` — 3, `/schedule` — 1, `/courses` — 1.
- stdout `ls` содержит `exists.txt`, stderr сообщает об отсутствующем файле.
- Неэкранированная переменная распадается на `my` и `log.txt`.
- Healthcheck: основной лог — 1/stderr; healthy — 0/stdout; отсутствующий — 2/stderr.
- Ctrl-C в `tail -f` не останавливает фоновый генератор.
- Checker: испорченный файл — 1, восстановленный — 0.

## Расследование: почему не сохраняется выбор курсов?

Студенты пишут: «myITMO лежит, расписание не составить».
Сгруппируйте ERROR по пятому полю: какие события объединяют неудачные запросы?
Откройте `my log.txt` с правильными кавычками. Сравните `active` с `limit`,
посмотрите на `waiting` и `incoming_rps`. Объясните, почему `/health` успешен.
Сформулируйте вывод и предложите следующий шаг диагностики.

Самопроверка: 5 событий `db_pool_timeout`; после открытия выбора заняты 20 из 20
соединений, 180 запросов ждут. Приложение не получает соединение вовремя,
поэтому не сохраняет выбор и не загружает расписание. `/health` не использует БД.
Чтобы выяснить, почему соединения долго заняты, нужно исследовать запросы,
блокировки и освобождение соединений. «База выключена» из этих данных не следует.

## Короткий итог дежурства (ещё 5 минут)

Без копирования готового вывода напишите три предложения: что не работало,
какие данные это подтверждают, что проверять дальше. Не предлагайте исправление,
для которого ещё нет доказательств. Сохраните ответ за пределами сбрасываемых
демо-файлов, если хотите оставить его после reset.

Дополнительная проверка: посчитайте все запросы `/enroll`, затем только неудачные.
Ожидается 4 и 3. Можно ли переносить долю 3/4 из учебной выборки на весь сервис?
Нет: это десять специально подготовленных событий, не репрезентативная статистика.
