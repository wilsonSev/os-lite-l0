# OS Lite H0 — почему упал myITMO во время выбора курсов?

Готовая площадка для интерактивной лекции на 90 минут. Коллега клонирует
репозиторий, запускает `./setup` и получает те же данные и ответы.

## Как проводить лекцию

Начните с [подготовки ведущего](lecturer/preparation.md), затем откройте
[«Первое дежурство»: полный сценарий на 90 минут](lecturer/runbook.md).
В нём есть реплики, мысли для слайдов, команды, прогнозы аудитории и развязка.
Shell-расследование работает локально. Docker-блок проводится только после
отдельного успешного прогона в том же окружении; `setup` Docker не устанавливает.

## Быстрый старт

В Bash-терминале Linux, macOS или Linux внутри WSL:

```bash
git clone <URL-вашего-репозитория> os-lite-h0
cd os-lite-h0
./setup
```

Нужны Bash 3.2+ и обычные Unix-утилиты. Установки пакетов, sudo и сеть для
`setup` не нужны. Для проведения примеров откройте `bash` (особенно если
обычный терминал использует zsh), затем `export LC_ALL=C TZ=UTC`.
Для дальнейших лабораторных по Linux используйте Linux-окружение.

`./setup` проверяет инструменты, сбрасывает демонстрационные файлы и запускает
локальный демо-чекер. Повторный запуск сбрасывает демо, но сохраняет `src/`.
Если вы меняли `src/hello.txt`, чекер может завершиться FAIL — это ожидаемо.

## Что за сервис

**myITMO («Мой ИТМО»), учебная симуляция выбора курсов.** Открылась запись
на курсы: студенты одновременно смотрят варианты, выбирают группы и пытаются
собрать расписание. В чате: «Мой ИТМО лежит! Выбор не сохраняется, расписания нет!».
Мы играем роль дежурной команды: есть терминал, журнал запросов и диагностический
снимок. Нужно выяснить, какие действия недоступны и что мешает их выполнить.

Все endpoints, события, цифры и архитектура ниже придуманы для занятия.
Это не описание настоящего сбоя или внутреннего устройства myITMO.
Реального сервиса, HTTP-запросов к myITMO и студенческих данных здесь нет.

| Endpoint | Действие студента / системы | События в журнале |
|---|---|---|
| `/health` | Проверяет, работает ли процесс приложения | `health_ok`, 200 |
| `/courses` | Получает список доступных курсов | `courses_listed`, 200; `db_pool_timeout`, 503 |
| `/enroll` | Сохраняет выбор курса и группы | `course_selected`, 200; `db_pool_timeout`, 503 |
| `/schedule` | Загружает собранное расписание | `db_pool_timeout`, 503 |

Генератор — настоящий процесс, который дописывает вымышленные события в файл.
Сетевого сервера нет. Успешный `/health` означает только, что приложение отвечает;
в нашем сценарии эта проверка не обращается к базе данных.

Формат журнала запросов: `UTC-время LEVEL endpoint=/path status=CODE event=name`.
Между полями ровно один пробел: поэтому здесь уместен `cut -d' ' -f3`.
В произвольных логах с пробелами внутри полей такой разбор уже ненадёжен.

## Что выясняем на лекции

1. В журнале 10 запросов, из них 5 с ошибками. Среди ошибок чаще всего встречается
   сохранение выбора: 3 запроса `/enroll`, по одному `/schedule` и `/courses`.
2. У всех ошибок одна причина ожидания — `db_pool_timeout`: приложение не успело
   получить свободное соединение с базой данных.
3. В файле `my log.txt` лежит **фиксированный диагностический снимок**:
   до открытия выбора заняты 4 из 20 соединений, ожидающих запросов нет;
   после открытия заняты все 20, в ожидании 180 запросов. Входящий поток
   вырос с 15 до 800 запросов в секунду. Это метрики снимка, не расчёт по 10 строкам.
4. Вывод: в учебном инциденте исчерпан пул соединений с БД. Новые запросы ждут,
   получают таймаут и завершаются 503 — поэтому студенты не могут сохранить
   выбранные курсы и увидеть расписание. Сам процесс приложения продолжает жить.
5. По этим данным ещё нельзя сказать, почему соединения не освобождаются достаточно
   быстро: медленные запросы, блокировки или утечка требуют следующей проверки.
   Резкий рост нагрузки — наблюдение, а не доказательство единственной первопричины.

Пул — ограниченный набор соединений, через которые приложение работает с БД.
Для объяснения достаточно аналогии с 20 окнами обслуживания и очередью к ним.
Файл с пробелом помогает связать пример с кавычками с настоящим шагом расследования.
Диагностический снимок не обновляется генератором; его читают как улику исходного
инцидента. Живой лог нужен для `tail -f`, фоновых заданий и остановки процессов.
Мы завершаем расследование выводом; сброс демо не означает ремонт сервиса.

## Первая демонстрация

```bash
grep ' ERROR ' logs/myitmo.log | wc -l
# 5
grep ' ERROR ' logs/myitmo.log \
  | cut -d' ' -f3 | sort | uniq -c | sort -nr
# 3 endpoint=/enroll; 1 endpoint=/schedule; 1 endpoint=/courses
./scripts/healthcheck.bash
echo "$?"
# 1: в журнале есть ошибки — это ожидаемый инцидент
./check
# PASS (demo): проверка учебного файла, а не здоровья сервиса
```

`healthcheck.bash [путь-к-логу]` проверяет весь переданный непустой журнал:
0 — нет ERROR, 1 — найдены ERROR, 2 — вход недоступен/пуст или ошибка чтения.
Это простая проверка логов, не мониторинг текущего состояния сервиса.
Для успешного примера: `./scripts/healthcheck.bash fixtures/myitmo.log.healthy`.

## Живой лог и сброс

В одном интерактивном Bash:

```bash
./scripts/generate-log.bash &
GEN_PID=$!
tail -f logs/myitmo.log
# Нажмите Ctrl-C: остановится tail, генератор ещё работает.
jobs
kill "$GEN_PID"
wait "$GEN_PID"
./reset-demo
```

Генератор повторяет фиксированную последовательность с текущими UTC-метками,
по одному событию в секунду. Для вопросов с точными числами сначала остановите
генератор и выполните сброс. Второй генератор не запускается.

`reset-demo` восстанавливает лог, `my log.txt`, `exists.txt`; удаляет только
`output.txt`, `errors.txt`, `combined.txt`, `missing.txt` в корне площадки.
Не храните в этих файлах свою работу. Остальные файлы, включая `src/`, сохраняются.
Во время генерации сброс отказывается работать: сначала остановите процесс.
Не используются `pkill`, `git clean` или массовое удаление файлов.

**Зависшая блокировка:** после SIGKILL или аварийного выключения может остаться
`.runtime/log.lock`. Убедитесь, что генераторы этой копии действительно остановлены
(проверьте терминалы/процессы), затем выполните `rmdir .runtime/log.lock` и сброс.
Обычный Ctrl-C/TERM снимает блокировку автоматически.

## Чекер и необязательный Docker

`./check` — рабочая **учебная заглушка**, проверяет точное содержимое
`src/hello.txt`: `Hello, OS Lite!` и перевод строки. Это не официальный чекер H1
и не подтверждение настройки всего курса. Коды: 0 PASS, 1 FAIL, 2 ошибка вызова;
при запуске Docker также возможны собственные коды ошибок Docker.

До занятия, при доступной сети и запущенном Docker:

```bash
docker pull alpine:3.20
docker pull hello-world
./check --docker
```

На занятии:

```bash
docker run --pull=never --rm hello-world
cat check
./check --docker
```

Оба режима запускают один и тот же `scripts/demo-check.sh`. В Docker `src/` и
скрипт проверки примонтированы только для чтения. В будущем официальный образ
курса заменит эту ветку обёртки. Сейчас checker-скрипт тоже приходит с хоста —
в официальном образе он должен находиться внутри образа.
Тег Alpine фиксирован, но не закреплён по digest: это учебное окружение, а не
побайтово закреплённая сборка. `--pull=never` намеренно исключает скачивание на паре.
Без локального образа или Docker режим явно завершится ошибкой, без скрытой
подмены локальным запуском. Для офлайн-плана Б используйте `./check --local`.

Для отладки с сохранением контейнера (без `--rm`):

```bash
docker run --pull=never --name h0-debug \
  -v "$PWD/src:/workspace/src:ro" \
  -v "$PWD/scripts/demo-check.sh:/demo-check.sh:ro" \
  alpine:3.20 sh /demo-check.sh /workspace/src
docker ps -a
docker logs h0-debug
docker rm h0-debug
```

Имя `h0-debug` должно быть свободно. После обычного `--rm` контейнер удалён,
поэтому его уже не будет в `docker ps -a` и его логи так не прочитать.

## Как передать коллегам

Это самостоятельный Git-репозиторий. После проверки содержимого создайте пустой
удалённый репозиторий и выполните из этой папки:

```bash
git add .
git commit -m "Add OS Lite H0 playground"
git remote add origin <URL-вашего-репозитория>
git push -u origin main
```

Рабочие логи и результаты команд исключены через `.gitignore`, скрипты имеют
исполняемый бит, окончания строк закреплены LF. Коллегам достаточно быстрого
старта выше; README с URL можно обновить после публикации.
